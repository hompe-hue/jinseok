# C1 전달 파일 수정 완료

2026-10-14. 사용자 화면에서 CAL060/CAL061 프로젝트가 0KB이고 CRUISE M이 “The file is not a valid project file”로 열기를 거부했다. 실제 현재 보관본도 두 파일이 0바이트였으며 기존 ZIP은 중앙 디렉터리가 없어 읽히지 않았다. 처음 기록한 검증 해시와 이후 보관된 바이트가 일치하지 않았으므로 이전 전달 검증만으로 정상 파일이 제공됐다고 판단한 것은 잘못이었다. 손상이 발생한 정확한 시점은 확정하지 않았다.

C1 계수와 프로파일을 바꾸지 않고 원본 DIS80에서 다시 만들었다. 새 CAL060은 1,582,115바이트, CAL061은 1,527,907바이트, HOLD066은 1,690,437바이트다. 프로젝트 SHA256은 최초 정상 생성 시 계약에 기록한 값과 모두 같다. 파일을 임시 경로에 완성하고 닫은 후 fsync·ZIP 검사를 거쳐 최종 경로로 교체하도록 생성 코드를 바꿨다. 별도 패키지 코드도 모든 프로젝트의 예상 크기·해시와 내부 XML을 먼저 검사해 빈 파일의 포함을 차단한다.

수정된 ZIP은 11,972,823바이트, SHA256 `1aba49ded38703690a8d3f8111aff5abc7c6d0e7f5ca9f4acec387f5d64f1045`다. 같은 파일 항목의 버전2로 저장했고, 다시 내려받은 실제 바이트에 대해 전체 ZIP CRC, 모든 파일의 크기·해시, 프로젝트3개의 해시·XML을 검증했다. 모두 통과했다. 실제 CRUISE M 자체에서 열기·계산한 것은 아니므로 애플리케이션 열기 확인은 사용자 환경에서 남아 있다.

새 `C1_BoltEV_Execution_Repair_20261014.zip`을 다른 폴더에 압축 해제한다. 탐색기의 CAL060/CAL061 크기는 약1545/1492KB여야 한다. CAL060부터 열어 확인한 뒤 두 CAL 시험을 실행한다. battery·velocity·generator CSV를 시험별3개씩 받아 평가한다. HOLD066은 CAL 확인 이후 실행한다. 이미 완료된 입력 확인이나 보정 계수 적합을 반복하지 않는다.

코드: `scripts/build_C1_projects.py`의 원자적 프로젝트 저장, `scripts/package_C1_atomic.py`의 완성 바이트 검사·패키징. 실제 전달 검증은 `repair_audit.json`, 최신 파일 식별자는 `artifact_receipt.json`에 있다. 모델 검증 완료 여부는 여전히 false다.
